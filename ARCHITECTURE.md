Документ для того, кто будет этот код развивать. Не пересказ документации
Django, а разбор решений: что выбрано, из чего выбирали и что сломается,
если сделать иначе.

## 1. Настройки: три файла вместо одного

```
config/settings/
├── base.py   общее для всех сред
├── dev.py    from base import *  + DEBUG = True
└── prod.py   from base import *  + защита
```

Альтернатива — один `settings.py` с `if DEBUG:` внутри. Так делают, и это
работает ровно до первого раза, когда кто-то выложит проект с `DEBUG = True`.
При включённом DEBUG страница ошибки показывает трассировку, фрагменты кода и
все настройки, включая пароль от базы. Разделение файлов делает такую ошибку
заметной: чтобы её совершить, надо явно указать `config.settings.dev` на сервере.

`manage.py` по умолчанию берёт `dev`, `wsgi.py` — `prod`. Локально вы никогда
не запускаете боевые настройки случайно, а gunicorn никогда не поднимет
отладочные.

**Тонкость с `import *`.** Он тянет всё, включая функции `env` и `env_bool`.
Поэтому в `prod.py` работает `env_bool("SECURE_SSL_REDIRECT", True)` без
отдельного импорта. Линтер на это ругается — отсюда комментарии `# noqa: F403`.

## 2. Переменные окружения и пустая строка

```python
def env(key, default=""):
    value = os.environ.get(key, "")
    return value if value.strip() else default
```

Обычный `os.environ.get(key, default)` подставит default только если переменной
**нет**. Строка `DATABASE_URL=` в `.env` — это переменная, которая есть и равна
пустой строке. Django из неё собирает конфигурацию базы без `ENGINE` и падает
с `ImproperlyConfigured`. Мы уже наступали на эти грабли.

Правило, которое стоит запомнить: в конфигурации «пусто» и «не задано» должны
означать одно и то же, иначе пользователь настроек обязан помнить разницу.

**Почему `.env` не в git.** В нём пароль от базы, токен бота и SECRET_KEY.
Репозиторий переезжает, форкается, показывается на собеседовании. Секреты
живут только в окружении. В git — `.env.example` без значений.

## 3. Приложения и `apps/`

Django-приложение — это единица переиспользования. Разбивать проект на
приложения стоит по границам предметной области, а не по типам файлов.
У нас четыре плюс служебное:

| Приложение | За что отвечает |
|---|---|
| `common` | абстрактные модели, ничего своего не хранит |
| `core` | тексты сайта, опыт, страницы |
| `services` | направления, услуги, цены |
| `leads` | готовые вопросы и заявки |
| `notifications` | доставка уведомлений, моделей нет вообще |

Проверочный вопрос: смогу ли я выкинуть приложение и не сломать остальные?
`notifications` выкидывается — упадёт только импорт в `leads/signals.py`.
`leads` без `notifications` не живёт, и это осознанная связь в одну сторону:
заявки знают про уведомления, уведомления про заявки — нет. Обратная зависимость
превратила бы два приложения в одно.

**`ready()` в AppConfig.** Сигналы надо подключить один раз при старте:

```python
class LeadsConfig(AppConfig):
    def ready(self):
        from . import signals  # noqa
```

Импорт внутри метода, а не наверху файла, — не стилистика. На момент импорта
модуля `apps.py` реестр моделей ещё не построен, и `from .models import Lead`
на верхнем уровне выдаст `AppRegistryNotReady`.

## 4. Абстрактные модели

```python
class TimeStampedModel(models.Model):
    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)

    class Meta:
        abstract = True
```

`abstract = True` — ключевая строка. Без неё Django создаст **таблицу**
`TimeStampedModel`, а наследники получат связь через внешний ключ
(multi-table inheritance). Каждый запрос к `Service` начнёт делать JOIN
с родительской таблицей. С `abstract = True` таблицы нет: поля просто
копируются в наследников на уровне схемы.

`PublishableModel` даёт паре `is_active` + `order`. Это про интерфейс
владелицы сайта: у неё должна быть возможность **скрыть**, а не удалить.
Удаление необратимо и пугает; галочка — нет.

`SingletonModel` — модель ровно с одной строкой. `save()` жёстко ставит
`pk = 1`, `delete()` ничего не делает. В админке кнопки «добавить» и «удалить»
скрыты через `SingletonAdmin`. Это защита от состояния, в котором настроек сайта
две и непонятно, какая действует.

`load()` использует `get_or_create` — сайт открывается даже на пустой базе,
хотя записи ещё нет.

## 5. Миграции

Миграция — это питоновское описание изменения схемы. `makemigrations` его
генерирует, `migrate` применяет и записывает факт применения в таблицу
`django_migrations`.

Три правила:

1. **Файлы миграций коммитятся в git.** Это часть кода. Иначе на сервере схема
   будет собрана из другой последовательности шагов, чем локально.
2. **`makemigrations` на сервере не запускается.** Только `migrate`.
   Генерация — задача разработчика, применение — задача деплоя. Наш
   `entrypoint.sh` делает ровно `migrate`.
3. **Миграция с данными — тоже миграция.** Если понадобится переименовать
   значения в существующих строках, это делается `RunPython`, а не руками
   в базе, иначе на сервере данные останутся старыми.

Первую миграцию мы генерировали командой
`makemigrations core services leads` — с явным перечислением приложений.
Без аргументов Django обошёл бы все, включая свои, — результат тот же, но
явная форма показывает, что вы контролируете, где появились изменения.

## 6. Запросы к базе: где прячется N+1

На главной выводятся направления, а внутри каждого — услуги. Наивно это
N+1 запрос: один на список направлений и по одному на услуги каждого.
Четыре направления — пять запросов. Сорок — сорок один.

```python
ServiceCategory.objects.filter(is_active=True).prefetch_related("services")
```

`prefetch_related` делает **два** запроса независимо от количества категорий:
один за категориями, второй за всеми их услугами разом, и раскладывает
результат по объектам в питоне.

Разница с `select_related`: тот подставляет JOIN и работает только для
«многие к одному» (ForeignKey у нас, объект там). `prefetch_related` — для
«один ко многим» и «многие ко многим». В `ServiceDetailView` мы используем
`select_related("category")`, потому что у услуги ровно одна категория.

**Ловушка в нашем коде.** В шаблоне вызывается `category.active_services`:

```python
@property
def active_services(self):
    return self.services.filter(is_active=True)
```

`.filter()` поверх предзагруженной связи создаёт **новый** запрос и обесценивает
`prefetch_related`. Правильно — предзагрузить сразу отфильтрованное:

```python
from django.db.models import Prefetch

ServiceCategory.objects.filter(is_active=True).prefetch_related(
    Prefetch("services", queryset=Service.objects.filter(is_active=True))
)
```

Оставлено как есть намеренно: на четырёх категориях разница неизмерима, а вам
полезно один раз увидеть, как выглядит эта ошибка вживую. Поставьте
`django-debug-toolbar` и посмотрите на счётчик запросов до и после — это
лучший способ прочувствовать.

## 7. Формы: где именно валидировать

`LeadForm` — `ModelForm`: поля берутся из модели, `save()` создаёт объект.
Валидация идёт слоями, и слой выбирается по тому, что нужно проверить:

- `clean_website()` — одно поле, независимо от остальных;
- `clean()` — связь **между** полями: «должен быть выбран вопрос ИЛИ написан свой».
  В `clean_<поле>` такую проверку сделать нельзя: порядок обработки полей
  не гарантирует, что второе уже разобрано.

**Honeypot.** Поле `website` спрятано CSS-классом `.hp` за границу экрана.
Человек его не видит и не заполняет, примитивный бот заполняет все поля формы.
Заполнено — форма невалидна.

Почему не капча: она отсеивает и людей тоже. На сайте, куда приходят
в стрессовой ситуации, каждое лишнее препятствие стоит обращений.
Honeypot ловит основную массу автоматики и не стоит пользователю ничего.

**Обязательность на двух уровнях.** `consent` объявлен `required=True` в форме
и `required` в HTML. Браузерная проверка — удобство, серверная — собственно
проверка. Первую отключают одной строкой в консоли.

## 8. Сигналы и транзакции

```python
@receiver(post_save, sender=Lead)
def send_lead_notification(sender, instance, created, **kwargs):
    if not created:
        return
    transaction.on_commit(_notify)
```

Сигнал выбран, чтобы уведомление уходило при **любом** способе создания заявки:
из формы, из админки, из скрипта. Явный вызов во вьюхе такой гарантии не даёт.

Обратная сторона: сигналы — неявный поток управления. Читая `views.py`, вы не
видите, что после `save()` кто-то шлёт письмо. Поэтому их держат в одном
предсказуемом месте (`signals.py`) и не плодят.

**`transaction.on_commit` — самое важное здесь.** `post_save` срабатывает
внутри транзакции, до её фиксации. Если запрос обёрнут в `atomic`, а уведомление
уходит в фоновый поток, поток может обратиться к базе за заявкой раньше, чем
транзакция закоммичена, — и не найти строку. Ошибка плавающая, воспроизводится
раз в сто отправок, ловится сутками. `on_commit` откладывает вызов до реальной
записи; если транзакции нет, функция выполняется сразу.

Запомните связку: **фоновая работа + сигнал = всегда `on_commit`**.

## 9. Фоновая отправка в потоке

```python
subject, body, url = build_lead_message(lead)   # синхронно, с обращением к базе
threading.Thread(target=dispatch, args=(...), daemon=True).start()
```

Без этого SMTP-сервер, задумавшийся на 20 секунд, держит HTTP-запрос, и клиент
всё это время смотрит на «Отправляю…».

Три решения внутри:

- **Текст собирается до потока.** `lead.question_text` дёргает внешний ключ,
  то есть базу. В потоке это означало бы отдельное соединение, которое некому
  закрыть. Собрали строки заранее — в поток уходят простые данные.
- **`daemon=True`.** Такой поток не мешает процессу завершиться. Плата: при
  перезапуске сервера недоотправленное уведомление теряется. Для одного
  сообщения в Telegram это приемлемо.
- **Исключения гасятся и логируются.** Заявка уже в базе. Показать человеку
  ошибку, потому что не отправилось письмо, — худший из вариантов.

**Где проходит граница.** Поток годится, пока задача одна, короткая и её потеря
не критична. Когда появится отправка документов клиентам, повторные попытки или
отложенные напоминания — нужен Celery с брокером. Переход дешёвый: заменяется
тело `notify_new_lead`, остальной код не знает, как именно доставляется
сообщение.

## 10. Кэш, который на самом деле счётчик

Антиспам считает заявки с одного IP:

```python
count = cache.get(f"lead-rate:{ip}", 0)
cache.set(key, count + 1, WINDOW * 60)
```

Стандартный `LocMemCache` живёт **внутри одного процесса**. Локально это
незаметно, а gunicorn запускает три воркера — получаются три независимых
счётчика, и фактический лимит втрое выше заявленного. Классическая ошибка,
которая не проявляется в разработке.

Поэтому в `base.py` включён `DatabaseCache`: таблица `site_cache`, общая для
всех процессов. Она создаётся командой `createcachetable`, которая вызывается
в `entrypoint.sh`.

Ещё одна тонкость — операция не атомарна. Между `get` и `set` другой процесс
может прочитать то же значение. Для антиспама это неважно: разница в одну-две
заявки. Для списания денег так писать нельзя — там нужен `F()`-объект или
`select_for_update`.

**IP за прокси.** `REMOTE_ADDR` за Caddy будет адресом самого Caddy — один и тот
же для всех. Поэтому читается `X-Forwarded-For`. Заголовок подделывается
клиентом, так что доверять ему можно только когда точно известно, что запросы
идут через ваш прокси.

## 11. PostgreSQL вместо SQLite

Честно: по нагрузке этому сайту SQLite хватило бы с запасом. Реальные причины
перейти на Postgres — другие.

- **SQLite блокирует всю базу на запись.** Одна запись — все остальные ждут.
  На десятке заявок в день незаметно, но поведение принципиально другое.
- **Файл базы привязан к диску.** На бесплатных тарифах PaaS файловая система
  часто эфемерна: контейнер перезапустился — базы нет. Управляемый Postgres
  (Neon, Supabase) живёт отдельно от контейнера и переживает любые деплои.
  Это, пожалуй, главный аргумент.
- **Типы данных.** SQLite хранит почти всё как текст и не проверяет длину полей.
  Postgres типы соблюдает, и ошибка вылезает при вставке, а не через полгода.

Переключение — одна переменная `DATABASE_URL`. Так работает потому, что весь
ORM написан поверх абстракции над бэкендами, а `dj_database_url` разбирает
строку в словарь. Ни одна строка моделей при переезде не меняется — вот ради
чего терпят многословность Django.

`conn_max_age=600` — соединение переиспользуется десять минут вместо того,
чтобы открываться на каждый запрос. Установка соединения с Postgres дороже
запроса, для SQLite смысла не имеет.

В боевом compose у сервиса `db` **нет** секции `ports`. Контейнеры одной сети
видят друг друга по имени сервиса, а наружу база торчать не должна: открытый
5432 с паролем `lawyer_dev` находят сканеры за часы. В dev-compose порт открыт
сознательно — чтобы `manage.py` из локального venv видел базу.

## 12. Статика и WhiteNoise

Три разных понятия, которые легко перепутать:

- `STATICFILES_DIRS` — где лежат **исходники** (`static/`);
- `STATIC_ROOT` — куда `collectstatic` их **складывает** (`staticfiles/`);
- `STATIC_URL` — по какому адресу они **отдаются**.

`collectstatic` собирает в одну папку вашу статику, файлы админки и всех
библиотек. В git попадает `static/`, `staticfiles/` — в `.gitignore`.

WhiteNoise позволяет Django отдавать статику самостоятельно, без отдельного
nginx. Для сайта такого размера это снимает целый слой инфраструктуры.

**Почему в dev другое хранилище.** В `base.py` стоит
`CompressedManifestStaticFilesStorage`: он дописывает к именам файлов хеш
содержимого (`styles.a1b2c3.css`), чтобы браузер кэшировал их вечно и при этом
мгновенно видел обновления. Обратная сторона — файл, которого нет в манифесте,
вызывает ошибку. В разработке `collectstatic` никто не гоняет, поэтому `dev.py`
подменяет хранилище на простое. Классический источник загадочного
`Missing staticfiles manifest entry`.

## 13. Docker: что здесь неочевидно

```dockerfile
COPY requirements.txt requirements-postgres.txt ./
RUN pip install -r requirements-postgres.txt
COPY . .
```

Порядок не случаен. Docker кэширует слои и переиспользует их, пока не изменились
входные данные. Зависимости копируются и ставятся **до** копирования кода:
правка шаблона не инвалидирует слой с pip, и пересборка занимает секунды.
Скопируй мы `COPY . .` первой строкой — каждая правка означала бы полную
переустановку всех пакетов.

**Непривилегированный пользователь.** `USER appuser` — если кто-то получит
выполнение кода внутри контейнера, он не будет root. Дёшево, отключать незачем.

**Тома.** Именованные (`pg_data`) управляются Docker и переживают пересоздание
контейнера. Bind-mount (`.:/app`) подключает папку с хоста — нужен в разработке
ради живой перезагрузки и не нужен в проде, где код уже внутри образа.

**`depends_on: condition: service_healthy`.** Без условия Docker считает
зависимость выполненной, как только контейнер **запущен**. Postgres при этом
ещё инициализируется секунд десять, и Django падает на первой же миграции.
`healthcheck` с `pg_isready` заставляет дождаться готовности принимать запросы.

**ENTRYPOINT против CMD.** ENTRYPOINT — то, что выполняется всегда (миграции,
сборка статики). CMD — команда по умолчанию, которую compose переопределяет:
в проде gunicorn, в разработке `runserver`. Финальный `exec "$@"` в скрипте
запускает CMD, заменяя собой процесс скрипта, — иначе сигнал остановки
от Docker не дойдёт до gunicorn и контейнер будет убиваться по таймауту.

## 14. Безопасность в проде

`prod.py` включает то, что в разработке мешает:

- `ALLOWED_HOSTS` — Django отвергает запросы с чужим заголовком `Host`.
  Защита от отравления ссылок в письмах восстановления пароля.
- `SECURE_SSL_REDIRECT`, `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE` — куки
  не уходят по HTTP.
- `SECURE_HSTS_SECONDS` — браузер месяц не будет пытаться зайти по HTTP.
  **Осторожно:** откатить это нельзя, браузеры запомнили. Включайте, только когда
  HTTPS работает стабильно.
- `X_FRAME_OPTIONS = "DENY"` — сайт нельзя встроить в iframe (кликджекинг).
- `SECURE_PROXY_SSL_HEADER` — Django узнаёт о HTTPS из заголовка
  `X-Forwarded-Proto`, потому что до него запрос доходит уже расшифрованным.
  **Опасно без прокси:** заголовок подделывается, и Django поверит, что
  соединение защищено. Строка допустима только потому, что мы точно знаем:
  впереди стоит Caddy, который этот заголовок перезаписывает.

Перед каждым деплоем: `python manage.py check --deploy --settings=config.settings.prod`

## 15. Почта

SMTP-провайдер не даст отправить письмо «от имени» произвольного адреса:
проверяется совпадение отправителя с аутентифицированным аккаунтом. Отсюда
требование `DEFAULT_FROM_EMAIL == EMAIL_HOST_USER` для Gmail.

Пароль от аккаунта Google в SMTP не работает с 2022 года — нужен **пароль
приложения**, доступный только при включённой двухфакторной аутентификации.
16 символов, вводятся без пробелов.

Если появится свой домен, письма с него сначала будут падать в спам, пока не
настроены DNS-записи SPF и DKIM. Провайдер (Resend, Brevo, Mailgun) даёт их
готовыми — надо прописать у регистратора домена.

Именно из-за этой хрупкости почта у нас — второй канал, а не единственный.
Telegram доставляет мгновенно и не имеет спам-фильтра.

## 16. Куда расти

Порядок предложен по соотношению «польза / усилие»:

1. **Тесты.** Начните с `apps/leads`: форма без согласия не проходит, honeypot
   отсекает бота, лимит срабатывает на шестой заявке. Django даёт тестовый
   клиент и отдельную базу из коробки.
2. **`django-debug-toolbar`** в dev — увидите реальное число запросов.
   Заодно проверите пункт 6 про N+1.
3. **`Prefetch` с фильтром** — исправление той самой ошибки.
4. **Аналитика заявок** — сколько обращений принёс каждый готовый вопрос.
   `annotate(Count("leads"))` в админке; сейчас там `obj.leads.count()`
   в цикле, то есть N+1 в чистом виде.
5. **Sitemap и robots.txt** — `django.contrib.sitemaps` уже в комплекте.
6. **Celery**, когда фоновых задач станет больше одной.

## Упражнения

Задачи с возрастающей сложностью — каждая закрепляет что-то из документа.

1. Добавьте в `Service` поле «срок исполнения» и проведите его через
   миграцию, админку и шаблон. Полный цикл изменения модели.
2. Сделайте на главной блок «Частые вопросы» — новая модель в `core`
   с наследованием от `PublishableModel`.
3. Замените `prefetch_related("services")` на `Prefetch` с фильтром
   и убедитесь по debug-toolbar, что запросов стало меньше.
4. Напишите тест: заявка без галочки согласия не создаётся.
5. Добавьте бэкенд уведомлений, пишущий заявки в файл. Проверка на понимание
   того, зачем нужен общий интерфейс: остальной код меняться не должен.
